2 What Turborepo Gives You

Turborepo is a high-performance build system for JavaScript/TypeScript monorepos. It does not change how your code runs — it changes how your repository is organised and built.

Task Caching

Build outputs are cached by content hash. If nothing changed in packages/database, it is never rebuilt.

Parallel Execution

Turbo runs independent tasks simultaneously. Web build and mobile build run in parallel.

Shared Packages

Types, Prisma client, auth utilities, and ESLint/TS configs are defined once and imported by every app.

Remote Cache (free)

Vercel provides a free remote cache for Turborepo. CI never rebuilds already-cached packages.

5 Key Considerations Before Migrating

5.1 Prisma in a Shared Package — Most Complex Part

Prisma generates its client at build time. In a monorepo, the packages/database package owns the schema and runs prisma generate. The generated client is then imported by apps/web. The output field in schema.prisma must be an absolute or properly relative path inside the package.

Test this locally before any migration commit. If Prisma client paths are wrong, the web app will fail to import the client and the build will break. This is the highest-risk step.

5.2 The postinstall Hook

Your root package.json currently runs prisma generate && prisma migrate deploy on postinstall. In the monorepo this moves to packages/database. Turbo's pipeline (db:generate → build) replaces manual chaining. Vercel runs the root build script which Turbo orchestrates.

5.4 Next.js Middleware (proxy.ts)

Your proxy.ts file is actually a Next.js middleware (it should be named middleware.ts at the app root for proper Next.js detection). After migration it lives at apps/web/middleware.ts. The auth logic can be imported from @daily-tracker/auth, but the middleware wrapper stays in the web app.

5.5 Docker Build

Your Dockerfile uses output: 'standalone' for minimal image size. In the monorepo, the Dockerfile moves to apps/web/Dockerfile. The build context must be the repo root (not apps/web/) so Docker can access workspace packages. Update COPY statements to include packages/ directories.

5.6 shadcn/ui CLI (components.json)

The shadcn CLI reads components.json to know where to write components. After moving to apps/web/, always run the CLI from apps/web/, not the repo root. The alias paths in components.json remain relative to apps/web/ so no changes needed inside the file.

5.7 Vercel Cron Job

The vercel.json with your daily cron at 0 0 * * * moves into apps/web/vercel.json. Vercel detects it automatically when the project's root directory is set to apps/web. Zero changes required to the cron configuration itself.

9 Final Recommendation

Do Phase 1 + Phase 2 now. The repo restructure and shared packages have zero risk to production behavior and lay a solid foundation. The Vercel free tier fully supports Turborepo with remote caching at no extra cost.

Hold Phase 3 (mobile) until Phase 2 is stable. Rushing a mobile app into an unstable monorepo structure is the most common failure mode.

Skip Phase 4 (apps/api) entirely for now. Your Next.js API routes are perfectly capable of serving both web and mobile. A separate Hono backend is premature overhead without a concrete reason.

Biggest Risk

Prisma client generation in a shared package. The output path configuration in schema.prisma is the most error-prone step. Always test pnpm --filter @daily-tracker/database build locally before pushing to Vercel.

Lowest Risk

Vercel deployment. Vercel built and actively maintains Turborepo. The integration is first-class. Free tier is fully supported. Remote caching is free.
